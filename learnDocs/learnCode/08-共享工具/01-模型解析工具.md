模型解析工具位于 Shared 层的核心位置，为整个插件提供统一的模型选择、解析和回退机制。这些工具被 Agent 编排层、配置系统和工具实现广泛依赖。

---

## 核心职责

模型解析工具模块负责处理所有与 AI 模型选择相关的逻辑，是 oh-my-opencode 多模型编排能力的核心基础设施。其主要职责包括：

**模型解析与选择**：实现四层解析策略（用户覆盖 -> 类别默认 -> Provider 回退 -> 系统默认），确保在任何配置下都能找到可用的模型。通过 `model-resolver.ts` 和 `model-resolution-pipeline.ts` 实现智能的模型选择逻辑。

**Fallback 链管理**：定义每个 Agent 和任务类别的模型回退链。当首选模型不可用时，系统按优先级尝试备用模型，保证任务执行的连续性。`model-requirements.ts` 中定义了 Sisyphus、Hephaestus、Oracle 等所有 Agent 的 fallback 配置。

**模型能力检测**：动态检测模型支持的功能（thinking、temperature、toolCall 等），并根据检测结果调整调用参数。`model-capabilities.ts` 结合运行时元数据和启发式规则，提供准确的能力检测。

**错误处理与重试**：识别可重试的模型错误（rate limit、quota exceeded 等），自动触发 fallback 机制。`model-error-classifier.ts` 维护错误分类规则，`model-suggestion-retry.ts` 处理模型建议重试逻辑。

## 12 个模型工具文件

### 1. model-resolver.ts

模型解析的入口文件，提供两个核心函数：

- `resolveModel()`：基础解析，按优先级尝试 userModel -> inheritedModel -> systemDefault
- `resolveModelWithFallback()`：完整解析，集成 pipeline 的四层策略

```typescript
// src/shared/model-resolver.ts:36-42
export function resolveModel(input: ModelResolutionInput): string | undefined {
  return (
    normalizeModel(input.userModel) ??
    normalizeModel(input.inheritedModel) ??
    input.systemDefault
  )
}
```

该文件还包含 `normalizeFallbackModels()` 和 `flattenToFallbackModelStrings()`，用于处理混合类型的 fallback_models 配置。

### 2. model-resolution-pipeline.ts

解析流水线的核心实现，包含四层解析策略：

1. **Override 层**：UI 选择的模型或用户配置的覆盖模型
2. **Category Default 层**：任务类别的默认模型，支持模糊匹配
3. **Provider Fallback 层**：按 fallback 链尝试可用 provider
4. **System Default 层**：最终的系统默认模型

```typescript
// src/shared/model-resolution-pipeline.ts:40-60
export function resolveModelPipeline(
  request: ModelResolutionRequest,
): ModelResolutionResult | undefined {
  const attempted: string[] = []
  // ... 四层解析逻辑
  if (normalizedUiModel) {
    return { model: normalizedUiModel, provenance: "override" }
  }
  // ... 继续其他层
}
```

### 3. model-requirements.ts

定义所有 Agent 和任务类别的模型需求配置：

- `AGENT_MODEL_REQUIREMENTS`：Sisyphus、Hephaestus、Oracle 等 Agent 的 fallback 链
- `CATEGORY_MODEL_REQUIREMENTS`：visual-engineering、ultrabrain、deep 等类别的配置

每个配置包含 providers 列表、model 名称、variant、reasoningEffort 等参数。

### 4. model-availability.ts

处理模型可用性检查和获取：

- `fuzzyMatchModel()`：模糊匹配模型名称，支持 provider 过滤
- `isModelAvailable()`：检查指定模型是否可用
- `fetchAvailableModels()`：从缓存或 SDK 获取可用模型列表
- `getConnectedProviders()`：获取已连接的 provider 列表

模糊匹配优先级：精确匹配 > 精确模型 ID 匹配 > 最短名称匹配。

### 5. model-capabilities.ts

模型能力检测的核心文件：

- `getModelCapabilities()`：获取模型的完整能力信息
- 支持运行时元数据、bundled snapshot、启发式规则三种数据源
- 检测 thinking、temperature、toolCall、modalities 等能力

```typescript

    ?? bundledSnapshot.models[canonicalModelID]
  // ... 能力检测逻辑
}
```

### 6. model-capability-heuristics.ts

启发式模型家族检测：

- `HEURISTIC_MODEL_FAMILY_REGISTRY`：定义各模型家族的特征模式
- `detectHeuristicModelFamily()`：根据模型 ID 检测所属家族

支持 Claude、GPT、Gemini、Kimi、GLM 等主流模型家族，为能力检测提供后备规则。

### 7. model-capability-aliases.ts

模型 ID 别名解析系统：

- `EXACT_ALIAS_RULES`：精确别名规则（如 gemini-3.1-pro-high -> gemini-3.1-pro）
- `PATTERN_ALIAS_RULES`：模式匹配别名规则
- `resolveModelIDAlias()`：解析模型 ID 到规范形式

### 8. model-capability-guardrails.ts

模型能力的安全检查：

- `collectModelCapabilityGuardrailIssues()`：收集能力配置问题
- 检查别名目标是否存在、别名与 snapshot 冲突、内置模型依赖别名等问题

### 9. model-error-classifier.ts

模型错误分类与处理：

- `isRetryableModelError()`：判断错误是否可重试
- `shouldRetryError()`：是否应该触发 fallback 重试
- `getNextFallback()`：获取下一个 fallback 模型
- `selectFallbackProvider()`：选择最佳 fallback provider

维护 `RETRYABLE_ERROR_NAMES` 和 `RETRYABLE_MESSAGE_PATTERNS` 两个集合用于错误识别。

### 10. model-settings-compatibility.ts

模型设置兼容性处理：

- `resolveCompatibleModelSettings()`：将期望设置调整为模型支持的设置
- 处理 variant、reasoningEffort、temperature、topP、maxTokens、thinking 等字段
- 当设置不被支持时，自动降级到兼容值

### 11. model-normalization.ts

模型名称标准化：

- `normalizeModel()`：去除空白，返回 undefined 或标准化后的名称
- `normalizeModelID()`：将版本号格式从点号转换为横线

### 12. model-suggestion-retry.ts

模型建议重试机制：

- `parseModelSuggestion()`：从错误中解析模型建议
- `promptWithModelSuggestionRetry()`：带建议重试的 prompt 调用
- `promptSyncWithModelSuggestionRetry()`：同步版本的带重试 prompt

## 模型解析流程

模型解析遵循严格的四层优先级策略：

```
用户请求
    │
    ▼
┌─────────────────┐
│ 1. Override     │ ◄── UI 选择 / 用户配置覆盖
│   (userModel)   │
└────────┬────────┘
         │ 未匹配
         ▼
┌─────────────────┐
│ 2. Category     │ ◄── 任务类别默认模型
│   Default       │     (如 visual-engineering)
└────────┬────────┘
         │ 未匹配/不可用
         ▼
┌─────────────────┐
│ 3. Provider     │ ◄── Fallback 链遍历
│   Fallback      │     (Sisyphus: Opus → Kimi → GPT)
└────────┬────────┘
         │ 全部不可用
         ▼
┌─────────────────┐
│ 4. System       │ ◄── 系统默认模型
│   Default       │     (最终保底)
└─────────────────┘
```

每层解析都会记录 `provenance`（来源），用于调试和追踪模型选择路径。

## 关键代码片段

### 片段 1：四层解析策略实现

```typescript
// src/shared/model-resolution-pipeline.ts:49-100
const normalizedUiModel = normalizeModel(intent?.uiSelectedModel)
if (normalizedUiModel) {
  log("Model resolved via UI selection", { model: normalizedUiModel })
  return { model: normalizedUiModel, provenance: "override" }
}

const normalizedUserModel = normalizeModel(intent?.userModel)
if (normalizedUserModel) {
  log("Model resolved via config override", { model: normalizedUserModel })
  return { model: normalizedUserModel, provenance: "override" }
}

// Category default with fuzzy matching
const normalizedCategoryDefault = normalizeModel(intent?.categoryDefaultModel)
if (normalizedCategoryDefault) {
  attempted.push(normalizedCategoryDefault)
  const match = fuzzyMatchModel(normalizedCategoryDefault, availableModels)
  if (match) {
    return { model: match, provenance: "category-default", attempted }
  }
}
```

### 片段 2：Fallback 链遍历

```typescript
// src/shared/model-resolution-pipeline.ts:140-170
if (fallbackChain && fallbackChain.length > 0) {
  for (const entry of fallbackChain) {
    for (const provider of entry.providers) {
      const fullModel = `${provider}/${entry.model}`
      const match = fuzzyMatchModel(fullModel, availableModels, [provider])
      if (match) {
        return {
          model: match,
          provenance: "provider-fallback",
          variant: entry.variant,
          attempted,
        }
      }
    }
  }
}
```

### 片段 3：错误分类判断

```typescript
// src/shared/model-error-classifier.ts:101-121
export function isRetryableModelError(error: ErrorInfo): boolean {
  if (error.name) {
    const errorNameLower = error.name.toLowerCase()
    if (NON_RETRYABLE_ERROR_NAMES.has(errorNameLower)) {
      return false
    }
    if (RETRYABLE_ERROR_NAMES.has(errorNameLower)) {
      return true
    }
  }

  const msg = error.message?.toLowerCase() ?? ""
  return RETRYABLE_MESSAGE_PATTERNS.some((pattern) => msg.includes(pattern))
}
```

## 实战示例

### 示例 1: 自定义模型解析

```typescript
import { resolveModelWithFallback } from "./shared/model-resolver"
import { AGENT_MODEL_REQUIREMENTS } from "./shared/model-requirements"
import { fetchAvailableModels } from "./shared/model-availability"

async function customModelResolution() {
  // 获取可用模型
  const availableModels = await fetchAvailableModels(client)
  
  // 使用 Sisyphus 的 fallback 链
  const sisyphusConfig = AGENT_MODEL_REQUIREMENTS["sisyphus"]
  
  const result = resolveModelWithFallback({
    uiSelectedModel: undefined,           // 无 UI 选择
    userModel: "anthropic/claude-opus-4-6", // 用户首选
    userFallbackModels: ["openai/gpt-5.4"], // 用户自定义 fallback
    categoryDefaultModel: undefined,
    fallbackChain: sisyphusConfig.fallbackChain,
    availableModels,
    systemDefaultModel: "opencode/gpt-5-nano"
  })
  
  if (result) {
    console.log(`Selected: ${result.model}`)
    console.log(`Source: ${result.source}`)  // "override" | "category-default" | ...
    console.log(`Variant: ${result.variant}`) // "max" | "high" | ...
  }
}
```

### 示例 2: Fallback 链配置

        // 字符串形式

        // 对象形式，指定 variant

          "variant": "medium",

## 总结

模型解析工具模块是 oh-my-opencode 多模型编排能力的基石。通过 12 个精心设计的工具文件，实现了：

1. **智能的模型选择**：四层优先级策略确保总能找到可用模型
2. **灵活的 Fallback 机制**：支持 Agent 级别和类别级别的 fallback 链配置
3. **准确的能力检测**：结合运行时元数据、snapshot 和启发式规则
4. **健壮的错误处理**：自动识别可重试错误并触发 fallback

理解这些工具的工作原理，有助于开发者自定义模型配置、调试模型选择问题，以及扩展新的模型支持。
