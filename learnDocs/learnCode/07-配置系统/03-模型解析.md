模型解析流水线位于配置系统的最顶层，负责将用户的模型意图转换为实际可用的模型标识。它是连接配置层与执行层的关键桥梁。

## 核心职责

模型解析流水线承担着四大核心职责：

**意图解析**：接收来自 UI、配置文件、Category 定义等多渠道的模型选择意图，将其统一转换为标准化的模型请求格式。这包括处理用户显式指定的模型、Category 默认模型、以及动态选择的 fallback 链。

**可用性验证**：通过模糊匹配算法验证目标模型是否在用户当前连接的 Provider 中可用。系统会检查模型列表缓存，支持精确匹配、子串匹配和跨 Provider 匹配，确保选中的模型能够实际调用。

**Fallback 决策**：当首选模型不可用时，按照预定义的 4 步策略逐级降级：Override（用户显式指定）→ Category-default（分类默认）→ Provider-fallback（Provider 级联）→ System-default（系统兜底）。每一步都有明确的优先级和匹配逻辑。

**Provider 适配**：针对不同 Provider 的模型命名差异进行自动转换，例如将 `gpt-5.4` 转换为 Provider 特定的格式。同时处理 variant、reasoning effort 等模型参数，确保调用参数与目标模型兼容。

## 4 步 Fallback 流水线

### 1. Override (覆盖)

Override 是最高优先级的模型选择方式，完全绕过所有 fallback 逻辑。它有两个来源：

**UI 选择模型**：当用户在 OpenCode 界面中手动选择模型时，该选择通过 `uiSelectedModel` 传入。这通常用于 primary agent（如 Sisyphus），允许用户临时切换模型而不修改配置。

**用户配置模型**：用户在配置文件中为特定 Agent 显式指定的 `model` 字段，通过 `userModel` 传入。这是永久性的模型覆盖。

```typescript
// src/shared/model-resolution-pipeline.ts:49-59
const normalizedUiModel = normalizeModel(intent?.uiSelectedModel)
if (normalizedUiModel) {
  log("Model resolved via UI selection", { model: normalizedUiModel })
  return { model: normalizedUiModel, provenance: "override" }
}

const normalizedUserModel = normalizeModel(intent?.userModel)
if (normalizedUserModel) {
  log("Model resolved via config override", { model: normalizedUserModel })
  return { model: normalizedUserModel, provenance: "override" }
}
```

Override 阶段不进行可用性检查，直接返回用户指定的模型。这赋予了用户完全的控制权，即使选择的模型当前不可用也会尝试调用。

### 2. Category-default (分类默认)

当没有 Override 时，系统会尝试使用 Category 的默认模型。Category 是任务类型的抽象，如 `visual-engineering`、`deep`、`quick` 等。

```typescript
// src/shared/model-resolution-pipeline.ts:61-100
const normalizedCategoryDefault = normalizeModel(intent?.categoryDefaultModel)
if (normalizedCategoryDefault) {
  attempted.push(normalizedCategoryDefault)
  if (availableModels.size > 0) {
    const parts = normalizedCategoryDefault.split("/")
    const providerHint = parts.length >= 2 ? [parts[0]] : undefined
    const match = fuzzyMatchModel(normalizedCategoryDefault, availableModels, providerHint)
    if (match) {
      log("Model resolved via category default (fuzzy matched)", {
        original: normalizedCategoryDefault,
        matched: match,
      })
      return { model: match, provenance: "category-default", attempted }
    }
  }
  // ... 连接 Provider 检查逻辑
}
```

Category-default 阶段会进行可用性验证：
- 如果有可用模型列表，使用模糊匹配确认 Category 默认模型是否可用
- 如果没有可用模型列表（首次运行），检查目标 Provider 是否已连接
- 支持 Provider 特定的模型 ID 转换

### 3. Provider-fallback (提供者 Fallback)

当 Category 默认模型不可用时，进入 Provider-fallback 阶段。这是整个系统最复杂的部分，包含三级 fallback：

**用户自定义 fallback_models**：
```typescript
// src/shared/model-resolution-pipeline.ts:103-138
const userFallbackModels = intent?.userFallbackModels
if (userFallbackModels && userFallbackModels.length > 0) {
  // 遍历用户配置的 fallback_models，返回第一个可用的
  for (const model of userFallbackModels) {
    attempted.push(model)
    // 检查 Provider 连接状态或进行模糊匹配
    if (match) {
      return { model: match, provenance: "provider-fallback", attempted }
    }
  }
}
```

**硬编码 fallback 链**：
```typescript
// src/shared/model-resolution-pipeline.ts:140-207
if (fallbackChain && fallbackChain.length > 0) {
  for (const entry of fallbackChain) {
    for (const provider of entry.providers) {
      if (connectedSet.has(provider)) {
        const transformedModelId = transformModelForProvider(provider, entry.model)
        const model = `${provider}/${transformedModelId}`
        return { model, provenance: "provider-fallback", variant: entry.variant, attempted }
      }
    }
    // 跨 Provider 模糊匹配
    const crossProviderMatch = fuzzyMatchModel(entry.model, availableModels)
    if (crossProviderMatch) {
      return { model: crossProviderMatch, provenance: "provider-fallback", variant: entry.variant, attempted }
    }
  }
}
```

Fallback 链定义在 `AGENT_MODEL_REQUIREMENTS` 或 `CATEGORY_MODEL_REQUIREMENTS` 中，每个条目包含：
- `providers`: 支持的 Provider 列表（按优先级排序）
- `model`: 模型名称
- `variant`: 可选的 variant（如 `high`、`max`、`medium`）
- `reasoningEffort`: 推理强度配置
- `temperature`、`top_p`、`maxTokens`: 生成参数

### 4. System-default (系统默认)

当所有 fallback 都失败时，使用系统默认模型作为最终兜底：

```typescript
// src/shared/model-resolution-pipeline.ts:209-215
if (systemDefaultModel === undefined) {
  log("No model resolved - systemDefaultModel not configured")
  return undefined
}

log("Model resolved via system default", { model: systemDefaultModel })
return { model: systemDefaultModel, provenance: "system-default", attempted }
```

System-default 通常配置为广泛可用的模型，如 `claude-sonnet-4-6` 或 `gpt-5.4`，确保在任何情况下都能有一个可用的模型。

## 模型解析流程

完整的模型解析流程如下：

1. **输入准备**：收集 UI 选择、用户配置、Category 默认、系统默认等输入
2. **Override 检查**：优先使用用户显式指定的模型
3. **Category 默认检查**：验证 Category 配置的默认模型是否可用
4. **用户 Fallback 遍历**：检查用户自定义的 fallback_models 列表
5. **硬编码 Fallback 遍历**：按优先级检查 Agent/Category 的 fallback 链
6. **Provider 连接检查**：对于每个 fallback 条目，检查对应 Provider 是否已连接
7. **模型可用性验证**：使用模糊匹配确认模型在可用列表中
8. **跨 Provider 匹配**：尝试在其他 Provider 中找到相同或相似的模型
9. **系统默认兜底**：返回配置的默认模型
10. **结果返回**：包含选中的模型、来源、variant 和尝试过的模型列表

### 片段 3: 模糊匹配算法

```typescript
// src/shared/model-availability.ts:34-104
export function fuzzyMatchModel(
  target: string,
  available: Set<string>,
  providers?: string[],
): string | null {
  log("[fuzzyMatchModel] called", { target, availableCount: available.size, providers })

  if (available.size === 0) {
    return null
  }

  const targetNormalized = normalizeModelName(target)

  // 按 Provider 过滤
  let candidates = Array.from(available)
  if (providers && providers.length > 0) {
    const providerSet = new Set(providers)
    candidates = candidates.filter((model) => {
      const [provider] = model.split("/")
      return providerSet.has(provider)
    })
  }

  // 子串匹配
  const matches = candidates.filter((model) =>
    normalizeModelName(model).includes(targetNormalized),
  )

  if (matches.length === 0) {
    return null
  }

  // 优先级 1: 精确匹配
  const exactMatch = matches.find((model) => normalizeModelName(model) === targetNormalized)
  if (exactMatch) {
    return exactMatch
  }

  // 优先级 2: 精确模型 ID 匹配
  const exactModelIdMatches = matches.filter((model) => {
    const modelId = model.split("/").slice(1).join("/")
    return normalizeModelName(modelId) === targetNormalized
  })
  if (exactModelIdMatches.length > 0) {
    return exactModelIdMatches.reduce((shortest, current) =>
      current.length < shortest.length ? current : shortest,
    )
  }

  // 优先级 3: 最短匹配（最具体）
  return matches.reduce((shortest, current) =>
    current.length < shortest.length ? current : shortest,
  )
}
```

## 依赖关系

模型解析流水线依赖以下组件：

**配置系统**：
- Schema 系统提供 `FallbackModelObject` 类型定义
- 配置加载器提供用户自定义的 `fallback_models` 配置
- Category 系统提供默认模型映射

**Provider 系统**：
- Provider 模型 ID 转换器处理不同 Provider 的命名差异
- 已连接 Provider 缓存提供当前可用的 Provider 列表
- 模型列表缓存提供可用模型集合

**Agent 系统**：
- Agent 定义提供每个 Agent 的 fallback 链配置
- Category 定义提供任务类型到模型的映射

**工具系统**：
- 日志记录器用于调试模型解析过程
- 数据路径解析器定位缓存文件

### 示例 1: Category 路由

假设用户执行 `ultrawork` 命令，Sisyphus 需要将任务委托给 Explore Agent 处理代码搜索：

```typescript

    "anthropic/claude-haiku-4-5",

```

解析流程：
1. Override：无 UI 选择或用户配置，跳过
2. Category-default：`opencode/minimax-m2.5` 在可用列表中，模糊匹配成功，返回

如果 `minimax-m2.5` 不可用：
```typescript
// availableModels 不包含 minimax
const result = resolveModelWithFallback({
  ...input,
  availableModels: new Set(["anthropic/claude-haiku-4-5", "opencode/gpt-5-nano"])
})
// 进入 Step 3: Provider-fallback
// 遍历 CATEGORY_MODEL_REQUIREMENTS["quick"].fallbackChain
// 找到第一个可用模型返回
```

### 示例 2: Provider Fallback

假设 Sisyphus Agent 被调用，但用户的首选模型不可用：

```typescript
// 场景：Sisyphus 被调用，用户配置了 fallback_models
const input: ExtendedModelResolutionInput = {
  uiSelectedModel: undefined,
  userModel: "anthropic/claude-opus-4-6",  // 用户首选
  userFallbackModels: [
    "opencode/kimi-k2.5",
    "openai/gpt-5.4",
    "zai-coding-plan/glm-5"
  ],
  categoryDefaultModel: undefined,
  fallbackChain: AGENT_MODEL_REQUIREMENTS["sisyphus"].fallbackChain,
  availableModels: new Set([
    "openai/gpt-5.4",
    "openai/gpt-5.4-mini",
    "zai-coding-plan/glm-5"
  ]),
  systemDefaultModel: "openai/gpt-5.4"
}

const result = resolveModelWithFallback(input)
// 结果：{ model: "openai/gpt-5.4", source: "override", attempted: [] }
```

解析流程：
1. Override：`userModel` 为 `anthropic/claude-opus-4-6`，直接返回

如果用户未配置 `userModel`：
```typescript
const inputWithoutOverride = { ...input, userModel: undefined }
const result = resolveModelWithFallback(inputWithoutOverride)
// Step 1: 无 Override
// Step 2: 无 Category-default
// Step 3: 遍历 userFallbackModels
//   - "opencode/kimi-k2.5": 不在 availableModels 中
//   - "openai/gpt-5.4": 模糊匹配成功！
// 结果：{ model: "openai/gpt-5.4", source: "provider-fallback", attempted: ["opencode/kimi-k2.5"] }
```

如果用户也未配置 `userFallbackModels`：
```typescript
const inputMinimal = {
  ...input,
  userModel: undefined,
  userFallbackModels: undefined
}
const result = resolveModelWithFallback(inputMinimal)
// Step 3: 使用 AGENT_MODEL_REQUIREMENTS["sisyphus"].fallbackChain
//   - Entry 1: anthropic/claude-opus-4-6 - anthropic 未连接
//   - Entry 2: opencode-go/kimi-k2.5 - opencode-go 未连接
//   - Entry 3: kimi-for-coding/k2p5 - 未连接
//   - Entry 4: opencode/kimi-k2.5 - 不在 availableModels
//   - Entry 5: openai/gpt-5.4 - openai 已连接，模糊匹配成功！
// 结果：{ model: "openai/gpt-5.4", source: "provider-fallback", variant: "medium", attempted: [] }
```
