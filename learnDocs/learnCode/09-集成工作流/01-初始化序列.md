## 核心职责

初始化序列是 Oh My OpenCode 插件的核心启动流程，负责将分散的组件组装成一个完整的可运行系统。它采用严格的 5 步顺序执行，每一步都建立在前一步的基础上，确保依赖关系正确解析。

第一步加载配置，从用户级和项目级配置文件中读取并合并设置，建立整个系统的运行参数。第二步创建管理器，初始化 Tmux 会话管理、后台任务管理、Skill MCP 管理等核心服务。第三步注册工具，构建包含 26 个内置工具的注册表，并加载用户自定义技能。第四步创建钩子，组装 48 个生命周期钩子，形成 3 层钩子体系。最后一步创建插件接口，将 OpenCode 的 8 个钩子处理器与内部系统连接起来。

这个序列的设计遵循依赖注入原则，每个步骤都接收前一步的输出作为输入，形成清晰的数据流。任何一步的失败都会导致整个初始化失败，确保系统不会在半初始化状态下运行。

## 5 步初始化详解

### Step 1: loadPluginConfig

配置加载是初始化的第一步，负责从文件系统中读取并合并配置。它采用多层配置架构，优先级从高到低依次为：项目配置 > 用户配置 > 默认值。

```typescript
// src/index.ts 第 32 行
const pluginConfig = loadPluginConfig(ctx.directory, ctx);
```

配置加载的具体流程在 `src/plugin-config.ts` 中实现。首先检测用户级配置文件（位于 `~/.config/opencode/`），然后检测项目级配置文件（位于 `.opencode/`）。系统支持 JSONC 格式，允许注释和尾随逗号。

配置合并采用智能策略：对于 `agents` 和 `categories` 使用深度合并，对于 `disabled_*` 数组使用集合去重合并，其他字段则直接覆盖。这种设计允许用户配置和项目配置协同工作，而不是简单地相互替代。

```typescript
// src/plugin-config.ts 第 112-159 行
export function mergeConfigs(
  base: OhMyOpenCodeConfig,
  override: OhMyOpenCodeConfig
): OhMyOpenCodeConfig {
  return {
    ...base,
    ...override,
    agents: deepMerge(base.agents, override.agents),
    categories: deepMerge(base.categories, override.categories),
    disabled_agents: [...new Set([...base.disabled_agents ?? [], ...override.disabled_agents ?? []])],
    // ... 其他 disabled_* 字段类似处理
  };
}
```

### Step 2: createManagers

管理器创建是第二步，初始化插件运行所需的核心服务。这一步创建了四个关键管理器，每个负责不同的子系统。

```typescript
// src/index.ts 第 50-56 行
const managers = createManagers({
  ctx,
  pluginConfig,
  tmuxConfig,
  modelCacheState,
  backgroundNotificationHookEnabled: isHookEnabled("background-notification"),
});
```

**TmuxSessionManager**：管理终端会话，支持交互式命令执行、TUI 应用和调试器。它维护一个会话池，确保多个后台代理可以并行运行而不会相互干扰。

**BackgroundManager**：后台任务管理的核心，负责代理的并行执行、任务队列管理和结果聚合。它支持最多 5 个并发任务（可配置），并在任务完成时通知父会话。

**SkillMcpManager**：管理 Skill 内嵌的 MCP 服务器。与全局 MCP 不同，Skill MCP 按需启动，任务完成后自动关闭，避免上下文膨胀。

**ConfigHandler**：处理 OpenCode 的 `config` 钩子，提供配置项的读取和验证服务。

### Step 3: createTools

工具创建是第三步，构建插件的工具生态系统。这一步创建了 26 个内置工具的注册表，并加载用户自定义 Skill。

```typescript
// src/index.ts 第 58-62 行
const toolsResult = await createTools({
  ctx,
  pluginConfig,
  managers,
});
```

工具创建流程分为三个阶段：

1. **SkillContext 创建**：扫描 `.opencode/skills/` 和 `~/.config/opencode/skills/` 目录，加载所有 Skill。每个 Skill 包含系统指令、嵌入式 MCP 定义和权限配置。

2. **AvailableCategories 创建**：根据配置生成分类映射，将任务类别（如 `visual-engineering`、`deep`、`quick`）映射到具体的模型选择策略。

3. **ToolRegistry 创建**：注册所有内置工具，包括 LSP 工具、AST-Grep 工具、Tmux 工具、MCP 工具等。然后根据 `disabled_tools` 配置过滤掉被禁用的工具。

```typescript
// src/create-tools.ts 第 29-42 行
const skillContext = await createSkillContext({
  directory: ctx.directory,
  pluginConfig,
});

const availableCategories = createAvailableCategories(pluginConfig);

const { filteredTools, taskSystemEnabled } = createToolRegistry({
  ctx,
  pluginConfig,
  managers,
  skillContext,
  availableCategories,
});
```

### Step 4: createHooks

钩子创建是第四步，组装 48 个生命周期钩子，形成完整的钩子体系。这一步是插件功能的核心，决定了插件如何介入 OpenCode 的各个生命周期阶段。

```typescript
// src/index.ts 第 64-73 行
const hooks = createHooks({
  ctx,
  pluginConfig,
  modelCacheState,
  backgroundManager: managers.backgroundManager,
  isHookEnabled,
  safeHookEnabled,
  mergedSkills: toolsResult.mergedSkills,
  availableSkills: toolsResult.availableSkills,
});
```

钩子体系分为三层：

**Core Hooks（39 个）**：核心钩子层，包括会话钩子（23 个）、工具守卫钩子（12 个）和转换钩子（4 个）。会话钩子处理上下文窗口监控、思考模式、模型回退等；工具守卫钩子在工具执行前后进行拦截和增强；转换钩子修改消息流和系统提示。

**Continuation Hooks（7 个）**：延续钩子层，处理任务延续、会话压缩、自动斜杠命令等高级功能。这些钩子确保长时间运行的任务可以正确恢复和继续。

**Skill Hooks（2 个）**：Skill 钩子层，提供分类提醒和自动命令功能，将 Skill 的能力注入到会话中。

### Step 5: createPluginInterface

插件接口创建是最后一步，将内部钩子体系映射到 OpenCode 的 8 个标准钩子处理器。这一步是插件与 OpenCode 集成的关键桥梁。

```typescript
// src/index.ts 第 81-88 行
const pluginInterface = createPluginInterface({
  ctx,
  pluginConfig,
  firstMessageVariantGate,
  managers,
  hooks,
  tools: toolsResult.filteredTools,
});
```

OpenCode 的 8 个钩子处理器包括：

1. **config**：配置钩子，由 ConfigHandler 处理
2. **tool**：工具钩子，暴露所有注册的工具
3. **chat.message**：消息钩子，处理会话消息和首消息变体
4. **chat.params**：参数钩子，调整 Anthropic  effort 级别
5. **chat.headers**：请求头钩子，注入 Copilot x-initiator
6. **event**：事件钩子，处理会话生命周期事件
7. **tool.execute.before**：工具执行前钩子，进行守卫检查
8. **tool.execute.after**：工具执行后钩子，进行输出处理

```typescript
// src/plugin-interface.ts 第 32-77 行
return {
  tool: tools,
  "chat.params": async (input: unknown, output: unknown) => { /* ... */ },
  "chat.headers": createChatHeadersHandler({ ctx }),
  "chat.message": createChatMessageHandler({ ctx, pluginConfig, firstMessageVariantGate, hooks }),
  "experimental.chat.messages.transform": createMessagesTransformHandler({ hooks }),
  "experimental.chat.system.transform": createSystemTransformHandler(),
  config: managers.configHandler,
  event: createEventHandler({ ctx, pluginConfig, firstMessageVariantGate, managers, hooks }),
  "tool.execute.before": createToolExecuteBeforeHandler({ ctx, hooks }),
  "tool.execute.after": createToolExecuteAfterHandler({ ctx, hooks }),
};
```

## 初始化流程

完整的初始化流程遵循严格的顺序依赖：

1. **配置先行**：必须先加载配置，后续步骤都依赖配置参数
2. **管理器次之**：管理器提供服务能力，工具创建需要 BackgroundManager 和 TmuxSessionManager
3. **工具随后**：工具注册需要管理器支持，钩子创建需要工具结果中的 Skill 信息
4. **钩子接着**：钩子组装需要工具结果中的 Skill 列表
5. **接口最后**：接口创建需要所有前面的输出，特别是工具和钩子

这种设计确保了每个组件在创建时，其依赖已经准备就绪。任何循环依赖都会在编译期被发现，运行时的初始化失败通常是由于配置错误或资源不可用导致的。

### 片段 2: 配置加载与合并

```typescript
// src/plugin-config.ts 第 161-213 行
export function loadPluginConfig(
  directory: string,
  ctx: unknown
): OhMyOpenCodeConfig {
  // 用户级配置路径
  const configDir = getOpenCodeConfigDir({ binary: "opencode" });
  const userDetected = detectPluginConfigFile(configDir);
  const userConfigPath = userDetected.format !== "none"
    ? userDetected.path
    : path.join(configDir, "oh-my-opencode.json");

  // 项目级配置路径
  const projectBasePath = path.join(directory, ".opencode");
  const projectDetected = detectPluginConfigFile(projectBasePath);
  const projectConfigPath = projectDetected.format !== "none"
    ? projectDetected.path
    : path.join(projectBasePath, "oh-my-opencode.json");

  // 加载用户配置（基础）
  let config: OhMyOpenCodeConfig = loadConfigFromPath(userConfigPath, ctx) ?? {};

  // 用项目配置覆盖
  const projectConfig = loadConfigFromPath(projectConfigPath, ctx);
  if (projectConfig) {
    config = mergeConfigs(config, projectConfig);
  }

  log("Final merged config", {
    agents: config.agents,
    disabled_agents: config.disabled_agents,
  });
  return config;
}
```

### 片段 3: 钩子组装

```typescript
// src/create-hooks.ts 第 28-87 行
export function createHooks(args: {
  ctx: PluginContext;
  pluginConfig: OhMyOpenCodeConfig;
  modelCacheState: ModelCacheState;
  backgroundManager: BackgroundManager;
  isHookEnabled: (hookName: HookName) => boolean;
  safeHookEnabled: boolean;
  mergedSkills: LoadedSkill[];
  availableSkills: AvailableSkill[];
}) {
  // 创建三层钩子
  const core = createCoreHooks({
    ctx,
    pluginConfig,
    modelCacheState,
    isHookEnabled,
    safeHookEnabled,
  });

  const continuation = createContinuationHooks({
    ctx,
    pluginConfig,
    isHookEnabled,
    safeHookEnabled,
    backgroundManager,
    sessionRecovery: core.sessionRecovery,
  });

  const skill = createSkillHooks({
    ctx,
    pluginConfig,
    isHookEnabled,
    safeHookEnabled,
    mergedSkills,
    availableSkills,
  });

  // 合并所有钩子
  const hooks = { ...core, ...continuation, ...skill };

  return {
    ...hooks,
    disposeHooks: (): void => {
      disposeCreatedHooks(hooks);
    },
  };
}
```

### 示例 2: 初始化失败处理

当配置加载失败时，系统会优雅降级：

```typescript
// src/plugin-config.ts 第 69-110 行
export function loadConfigFromPath(
  configPath: string,
  _ctx: unknown
): OhMyOpenCodeConfig | null {
  try {
    if (fs.existsSync(configPath)) {
      const content = fs.readFileSync(configPath, "utf-8");
      const rawConfig = parseJsonc<Record<string, unknown>>(content);

      const result = OhMyOpenCodeConfigSchema.safeParse(rawConfig);

      if (result.success) {
        log(`Config loaded from ${configPath}`, { agents: result.data.agents });
        return result.data;
      }

      // 验证失败，尝试部分加载
      log(`Config validation error in ${configPath}:`, result.error.issues);
      const partialResult = parseConfigPartially(rawConfig);
      if (partialResult) {
        log(`Partial config loaded from ${configPath}`, { agents: partialResult.agents });
        return partialResult;
      }

      return null;
    }
  } catch (err) {
    const errorMsg = err instanceof Error ? err.message : String(err);
    log(`Error loading config from ${configPath}:`, err);
    addConfigLoadError({ path: configPath, error: errorMsg });
  }
  return null;
}
```

当某个配置文件加载失败时，系统会：
1. 记录详细的错误信息
2. 尝试部分加载（跳过无效的配置段）
3. 如果完全无法加载，返回 null，让调用方使用默认配置

这种设计确保了即使配置有问题，插件也能以降级模式运行，而不是直接崩溃。
