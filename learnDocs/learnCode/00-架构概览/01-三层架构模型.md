## 核心职责

三层分离架构的核心思想是**关注点分离**与**可替换性**。每一层都有明确的边界和职责，层与层之间通过定义良好的接口交互。

**Layer 1 (MODEL)** 负责与 LLM 提供商交互，处理模型选择、可用性检查、降级策略。它不关心上层用模型做什么，只保证"给定一个请求，返回一个可用的模型实例"。

**Layer 2 (AGENT)** 实现推理循环和任务编排。Agent 是"思考者"，决定调用什么工具、如何分解任务、何时委托子代理。Agent 不直接操作文件系统或执行命令，而是通过 Harness 提供的工具完成。

**Layer 3 (HARNESS)** 是执行平台，提供工具实现、生命周期钩子、会话管理。它是"执行者"，负责把 Agent 的决策转化为实际操作，同时通过钩子系统注入横切关注点（如安全校验、上下文注入、错误恢复）。

这种分离让调试变得清晰：模型问题去 Layer 1 查 fallback 链，逻辑问题去 Layer 2 查 Agent 提示词，工具问题去 Layer 3 查具体实现。

## 三层模型详解

### Layer 1: MODEL (语言模型)

Model 层负责**模型选择**与**可用性保证**。当上层请求一个 Agent 执行时，Model 层通过 4 步优先级解析出实际使用的模型：

1. **Override**: 用户通过 UI 或配置显式指定的模型
2. **Category Default**: 任务分类（如 `visual-engineering`）配置的默认模型
3. **Provider Fallback**: Agent 定义的 fallback 链，按提供商优先级尝试
4. **System Default**: 系统级最终兜底模型

关键实现位于 `src/shared/model-resolution-pipeline.ts`（第40-216行）。该管道会检查模型可用性（通过 `availableModels` 集合或 `connectedProviders` 缓存），并在必要时进行模糊匹配（`fuzzyMatchModel`）。

每个 Agent 在 `src/shared/model-requirements.ts` 中定义了自己的 fallback 链。例如 Sisyphus 的 fallback 链（第22-44行）：
- 优先尝试 Claude Opus 4.6 (max)
- 然后是 Kimi K2.5
- 接着是 GPT-5.4 (medium)
- 最后是 GLM-5 和 big-pickle

这种设计让 OMO 可以在不同提供商之间无缝切换，即使某个提供商宕机，任务也能继续执行。

### Layer 2: AGENT (推理循环)

Agent 层实现**任务理解**与**编排决策**。OMO 包含 11 个专门的 Agent，每个都有特定的职责和工具限制：

| Agent | 职责 | 模型偏好 | 工具限制 |
|-------|------|----------|----------|
| **Sisyphus** | 主编排器，决策与委托 | Claude/Kimi/GLM | 无限制 |
| **Hephaestus** | 深度自主执行 | GPT-5.4 | 无限制 |
| **Prometheus** | 战略规划与访谈 | Claude Opus | 只读 |
| **Atlas** | Todo 列表执行 | Claude Sonnet | 禁止 task/call_omo_agent |
| **Oracle** | 架构咨询 | GPT-5.4 | 只读 |
| **Librarian** | 文档/OSS 搜索 | MiniMax | 禁止 write/edit/task |
| **Explore** | 代码库搜索 | Grok | 禁止 write/edit/task |
| **Metis** | 计划审查 | Claude Opus | 禁止 write/edit/task |
| **Momus** | 严格代码审查 | GPT-5.4 xhigh | 禁止 write/edit/task |
| **Multimodal-Looker** | 视觉分析 | GPT-5.3-codex | 只允许 read |
| **Sisyphus-Junior** | 分类任务执行 | 按 category | 无限制 |

Agent 定义位于 `src/agents/` 目录，通过工厂模式创建（`createXXXAgent`）。Agent 配置包含 instructions、model、temperature、tool restrictions 等。

Agent 间的委托通过 `task` 工具（`src/tools/delegate-task/tools.ts`）实现，支持同步（`run_in_background=false`）和异步（`run_in_background=true`）两种模式。

### Layer 3: HARNESS (执行平台)

Harness 层是**工具实现**与**生命周期管理**的集合。它包含：

**Tools (26个)**：
- **代码工具**: `ast_grep_search/replace`, `grep`, `glob`, `lsp_*`
- **会话工具**: `session_list/read/search/info`
- **任务工具**: `task` (委托), `call_omo_agent`, `background_output/cancel`
- **系统工具**: `interactive_bash`, `look_at`, `skill`, `skill_mcp`
- **编辑工具**: `hashline_edit` (带内容哈希校验)

**Hooks (48个)**：
- **Session Hooks (23)**: 上下文窗口监控、模型降级、Ralph Loop、Todo 强制继续等
- **Tool-Guard Hooks (12)**: 注释检查、规则注入、写文件保护、JSON 错误恢复等
- **Transform Hooks (4)**: Claude Code 兼容、关键词检测、思考块校验等
- **Continuation Hooks (7)**: 会话恢复、Atlas 编排、背景任务通知等
- **Skill Hooks (2)**: 分类技能提醒、自动斜杠命令

**基础设施**：
- **Tmux**: 交互式终端会话管理
- **MCP**: 内置 websearch (Exa)、context7 (文档)、grep_app (GitHub)
- **Skill System**: 嵌入式 MCP，按需加载

### 片段1: 模型解析管道 (4步优先级)

```typescript
// src/shared/model-resolution-pipeline.ts:40-63
export function resolveModelPipeline(
  request: ModelResolutionRequest,
): ModelResolutionResult | undefined {
  // Step 1: UI 选择的模型 (override)
  const normalizedUiModel = normalizeModel(intent?.uiSelectedModel)
  if (normalizedUiModel) {
    return { model: normalizedUiModel, provenance: "override" }
  }

  // Step 2: 用户配置的模型 (override)
  const normalizedUserModel = normalizeModel(intent?.userModel)
  if (normalizedUserModel) {
    return { model: normalizedUserModel, provenance: "override" }
  }

  // Step 3: 分类默认模型 (category-default)
  const normalizedCategoryDefault = normalizeModel(intent?.categoryDefaultModel)
  if (normalizedCategoryDefault) {
    const match = fuzzyMatchModel(normalizedCategoryDefault, availableModels)
    if (match) {
      return { model: match, provenance: "category-default" }
    }
  }

  // Step 4: Fallback 链 (provider-fallback) 和系统默认
  // ... 遍历 fallbackChain 和 systemDefaultModel
}
```

## 依赖关系

```
Layer 1 (MODEL)
    ↑ 被依赖
Layer 2 (AGENT)
    ↑ 被依赖
Layer 3 (HARNESS)
```

**依赖规则**：
- Layer 2 依赖 Layer 1: Agent 通过 `resolveModelPipeline` 获取模型
- Layer 3 依赖 Layer 2: Hooks 和 Tools 通过 Agent 配置了解模型限制
- Layer 3 不直接依赖 Layer 1: 模型选择对 Harness 透明，Harness 只接收最终模型

**数据流向**：
1. 用户请求 → Harness (keyword-detector, rules-injector)
2. Harness → Agent (Sisyphus 决策)
3. Agent → Model (解析出具体模型)
4. Model → Agent (返回模型实例)
5. Agent → Harness (调用 tools 执行)
6. Harness → 外部系统 (文件、LSP、MCP 等)

## 实战示例：使用三层模型诊断问题

### 场景：用户报告 "ultrawork 命令执行很慢"

**诊断流程**：

**Step 1: 确定问题在哪一层**
- 如果是特定模型响应慢 → **Layer 1 问题**
- 如果是 Agent 反复重试/委托 → **Layer 2 问题**
- 如果是工具执行慢（如 LSP）→ **Layer 3 问题**

**Step 2: 检查 Layer 1 (MODEL)**
```bash
# 查看日志确认实际使用的模型
tail /tmp/oh-my-opencode.log | grep "Model resolved"
# 输出: "Model resolved via provider-fallback" { model: "github-copilot/grok-code-fast-1" }
```
发现使用了 Grok Code Fast 1，但该模型当前延迟高。

**Step 3: 检查 Layer 2 (AGENT)**
```bash
# 查看 Explore Agent 的 fallback 链
grep -A 10 "explore:" src/shared/model-requirements.ts
# 发现 fallback 链: grok-code-fast-1 → minimax-m2.7 → claude-haiku-4-5
```
Grok 是第一优先级，但当前慢。应该让 Explore 跳过 Grok，直接使用 MiniMax。

**Step 4: 检查 Layer 3 (HARNESS)**
```bash
# 检查是否有 runtime-fallback hook 触发
grep "runtime-fallback" /tmp/oh-my-opencode.log
# 发现没有触发，说明模型可用但慢，不是不可用
```

**解决方案**：
1. **临时**: 在配置中禁用 Grok，强制使用 MiniMax
2. **长期**: 调整 `AGENT_MODEL_REQUIREMENTS` 中 Explore 的 fallback 链顺序

**验证修复**：
```bash
# 再次执行 ultrawork，检查日志
tail /tmp/oh-my-opencode.log | grep "Model resolved"
# 输出: "Model resolved via provider-fallback" { model: "opencode-go/minimax-m2.7" }
# 响应时间恢复正常
```
